# LLM 运营监控看板最终呈现方案

## 1. 页面定位

这张看板服务于 Zook 运营和技术运营人员，进入页面后应能依次回答五个问题：

1. 最近 48 小时整体调用是否正常？
2. Token 主要消耗在哪些 Model 和 Provider？
3. 哪些 Provider 或 Provider × Model 组合更慢、更不稳定？
4. 当前动态路由为什么按这个概率分流？
5. 选中某个对象后，它在 48 小时内具体发生了什么？

页面默认展示最近 `48h`，并在页头持续显示数据时区、最后更新时间和刷新状态。

## 2. 全局控制区

页头使用一行紧凑控制区：

- 时间范围：`24h / 48h / 7d / 30d`，默认 `48h`。
- 调用类型：`全部 / Chat / Embedding`，默认全部；延迟比较默认不混合不同调用类型。
- Provider：默认全部，可选择单个 Provider。
- Model：默认全部，可选择单个实际 Model。
- 自动刷新：默认开启，每 60 秒刷新一次；支持手动刷新。
- 数据状态：明确展示“最后更新于 HH:mm:ss”，请求失败时保留上次成功数据并提供重试。
- 数据覆盖：当选择范围早于系统实际开始记录的时间，持续显示“统计数据自 YYYY-MM-DD HH:mm 起可用”；图表把此前区间标为“无统计数据”，不画成零调用。

Provider 和 Model 筛选共同作用于运营指标。两者都选择时，页面自动进入 Provider × Model 交叉分析范围。动态路由表可以隐藏不匹配的行，但动态分和选择概率始终使用同一 Model 全部 route 的原始分母，不因 UI 筛选而重新计算。

交叉矩阵点击结果优先于当前 Provider/Model 筛选并同步更新筛选器；随后手动修改任一筛选器时，清除原矩阵选中态。自动刷新只清除已不再存在的选项，并明确提示原因。

所有标题和说明使用当前范围名称，不把 `7d` 或 `30d` 仍写成“48 小时”。`24h/48h` 按小时聚合，`7d/30d` 按天聚合；明细表分别最多 48 行或 30 行。

本页使用两个明确的 Model 维度：

- **Provider Model**：实际发给上游的模型标识，用于 Token、延迟和 Provider × Model 运营统计。
- **路由 Model**：Zook 配置中用于选择 route 的 common model key，用于动态路由评分和概率展示。

业务 scene route key 不作为 Model 排行维度。Provider Model 与路由 Model 不同的地方同时展示两者。

## 3. 第一屏：48 小时运营总览

### 3.1 六张关键指标卡

1. **上游调用次数**
   - 展示当前范围内实际发起的 LLM/Embedding 上游调用总数。
   - 辅助信息：成功、失败、超时和客户端取消数量。

2. **总 Token 消耗**
   - 展示 Provider 返回或 Zook 估算的 canonical `totalTokens`，不自行重复相加。
   - 辅助信息：Provider 原始统计占比与估算占比，避免把估算值误认为精确账单。

3. **成功率**
   - 展示可靠性成功率：`成功 ÷ (成功 + 失败 + 超时)`，客户端取消不进入分母。
   - 辅助信息：失败、超时、取消数量及最近一个时间桶的可靠性成功率。
   - 动态路由表中的“健康成功率”按最近健康窗口单独计算，不能与本指标混用。

4. **P50 首响应延迟**
   - 展示流式调用从发出请求到首个内容块的中位时间。
   - 说明：Embedding 和非流式调用不伪装成首响应数据；同时显示符合条件的样本数和覆盖率，无样本时显示 `—`。

5. **P50 总延迟**
   - 展示从发出请求到完整结束的中位时间，反映典型用户等待时长。

6. **P95 总延迟**
   - 展示最慢 5% 调用的边界，用于发现平均值掩盖的长尾问题。

当调用类型为“全部”时，首响应只显示 Streaming Chat；P50/P95 总延迟在同一指标卡内分别显示 Chat 与 Embedding 子值，不把两类调用合并计算一个百分位。

指标卡保持紧凑，不使用夸张字号；数字使用等宽数字样式，单位固定显示。

### 3.2 调用量与成功率趋势图

- `24h/48h` 使用小时点，`7d/30d` 使用天点。
- 柱形展示每个时间桶的调用次数。
- 折线展示每个时间桶的可靠性成功率。
- Tooltip 同时显示调用、成功、失败、超时、取消和可靠性成功率。
- 用途说明：判断流量变化是否伴随稳定性下降。

### 3.3 Token 消耗趋势图

- `24h/48h` 使用小时点，`7d/30d` 使用天点。
- 堆叠面积图展示 Prompt、可见输出和 Reasoning Token；其中可见输出为 `max(completionTokens - reasoningTokens, 0)`。
- canonical `totalTokens` 保持独立展示；若 breakdown 与总量无法对齐，显示“未分类差额”，不改写 Provider 总量。
- Tooltip 展示各类 Token、总 Token、Provider 原始/估算/缺失调用数。
- 用途说明：识别 Token 突增发生在输入、普通输出还是推理阶段。

## 4. 第二屏：Model 与 Provider 运营表现

### 4.1 Model Token 排行

**图表：** 横向堆叠条形图，按总 Token 从高到低展示 Provider Model；分段显示 Prompt、可见输出、Reasoning 和未分类差额。

**明细表：**

| 字段 | 说明 |
| --- | --- |
| Provider Model | 实际发给上游的 Model，不展示业务 scene route key |
| 类型 | Chat 或 Embedding |
| 调用次数 | 该 Model 的上游调用总数 |
| Prompt Token | 输入 Token |
| 可见输出 Token | Completion 扣除其中已包含的 Reasoning Token |
| Reasoning Token | 推理 Token |
| 未分类差额 | canonical 总量无法由已知 breakdown 对齐的 Token |
| 总 Token | Provider 返回或 Zook 估算的 canonical `totalTokens` |
| 单次平均 Token | 总 Token ÷ 调用次数 |
| 占全局比例 | 该 Model Token 占当前筛选范围的比例 |

用途说明：找出 Token 成本最高的 Model，以及消耗来自高频调用还是单次上下文过大。

### 4.2 Provider 运营表现

**图表：** 横向堆叠条形图，按总 Token 从高到低展示 Provider；分段显示 Prompt、可见输出、Reasoning 和未分类差额。

**明细表：**

| 字段 | 说明 |
| --- | --- |
| Provider | 实际承接流量的 Provider |
| 类型 | 当前行的 Chat 或 Embedding cohort；选择“全部”时分别成行，避免混合比较延迟 |
| 调用次数 | 该 Provider 的上游调用总数 |
| 成功率 | 成功调用占比 |
| Prompt Token | 输入 Token |
| 可见输出 Token | Completion 扣除其中已包含的 Reasoning Token |
| Reasoning Token | 推理 Token |
| 未分类差额 | canonical 总量无法由已知 breakdown 对齐的 Token |
| 总 Token | Provider 返回或 Zook 估算的 canonical `totalTokens` |
| 单次平均 Token | 总 Token ÷ 调用次数 |
| 占全局比例 | 该 Provider Token 占当前筛选范围的比例 |
| P50 首响应 | 仅流式样本；同时展示样本覆盖率 |
| P50 / P95 总延迟 | 当前调用类型内的典型与长尾完整耗时 |
| 承载流量占比 | 当前 Provider 调用数占同调用类型总数的比例 |

用途说明：查看 Token 流量实际落在哪些供应商，为容量、额度和商务决策提供依据。

## 5. 第三屏：动态路由决策

### 5.1 当前动态路由评分表

每一行代表一个实际 Model × Provider route。

| 字段 | 说明 |
| --- | --- |
| Model | 当前配置的实际 Model |
| Provider / Provider Model | 实际上游 route |
| 策略 | `auto` 或 `fixed` |
| 状态 | 启用、禁用或不可用；颜色之外同时显示文字 |
| 基础权重 | 人工配置的静态权重 |
| 健康样本 | 当前健康窗口样本数 |
| 动态成功率 | 当前健康窗口内的成功率 |
| 健康分 | 路由算法实际使用的健康分 |
| 动态分 | `基础权重 × 健康分 ÷ 100` |
| 期望流量 | 该 Model 下所有启用 route 动态分归一化后的概率 |
| 实际流量 | 所选时间范围内该 route 实际调用数占同 Model 调用数的比例 |
| 窗口最近错误 | 最近 100 个健康影响样本中的最后失败时间；窗口内无错误时显示“暂无” |

动态路由区明确标注这是**当前快照**，展示生成时间、配置 revision 和生效时间。所有数值直接来自后端 canonical 路由计算结果，前端不复算公式。

`auto` 策略展示：

```text
动态分 = 基础权重 × 健康分 ÷ 100
实际选择概率 = 当前 route 动态分 ÷ 同 Model 全部 selectionEligible route 动态分之和
```

如果所有可用 route 的动态分均为 0，明确显示“健康分全零，回退到基础权重归一化”，并展示回退后的真实概率。
如果 eligible route 连基础权重也无法形成正权重，则显示“无可路由 Provider”，不展示伪造的概率。

`fixed` 策略展示：

- 实际被选中的最高权重可用 route 为 `100%`，其他 route 为 `0%`。
- 健康分和动态分仍展示，但标记“仅观测，不参与 fixed 选择”。
- 如果没有启用 route 而进入现有兼容回退，显示醒目的“首条 route 兼容回退”选择原因，不伪装成正常动态分流。
- 权重相同时展示确定性的 tie-break 说明。

用途说明：解释“为什么当前流量这样分”，并对比算法期望概率与当前历史范围的真实流量占比。

### 5.2 实际流量与动态评分期望对比图

- 每个路由 Model 只使用一条 100% 堆叠条形，实色区块表示所选时间范围内各 Provider 的实际流量占比，同一 Provider 始终使用相同颜色。
- 当前动态评分推导出的期望流量不再单独占一行，而是在同一条形上使用深色竖线标出累计期望分界；竖线的形状与文字图例保证差异不只依赖颜色表达。
- 足够宽的区块直接显示实际占比；悬浮提示逐 Provider 展示实际流量、期望流量和百分点偏差，并明确当前快照与历史范围的时间口径不同。
- 配置在所选范围内发生过变更、健康样本不足或调用量过低时不产生偏差告警，只显示解释性提示。
- 用途说明：辅助发现分流偏差；不能用过去流量反证当前瞬时路由快照。

## 6. 第四屏：Provider × Model 交叉分析

### 6.1 交叉矩阵

矩阵行是 Provider，列是 Model。矩阵上方可切换指标：

- 调用次数
- 总 Token
- 成功率
- P50 总延迟
- P95 总延迟

每个单元格同时有数值和强弱色阶；无数据明确显示 `—`。点击任一单元格，会把该 Provider × Model 带入下方深度分析区。

用途说明：快速找出“同一 Model 在哪个 Provider 更慢”或“某个 Provider 的问题集中在哪些 Model”。

## 7. 可选对象深度分析

深度分析默认折叠，不重复占据首屏。只有选择 Provider、Provider Model 或交叉矩阵单元格后才展开；根据筛选或矩阵点击结果自动更新。标题明确显示当前范围，例如：

```text
百炼 Coding Plan × qwen3.6-plus · 最近 48 小时
```

### 7.1 当前对象指标

展示调用次数、总 Token、成功率、P50/P95 首响应、P50/P95 总延迟和单次平均 Token。

### 7.2 延迟趋势图

- 折线展示每个时间桶的 P50 与 P95 总延迟。
- 流式调用另以两条可切换折线展示 P50 与 P95 首响应。
- 图例可点击隐藏序列且支持键盘操作；Tooltip 展示精确值和样本数。
- 用途说明：判断延迟问题是持续性退化还是短时尖峰。

### 7.3 调用与稳定性趋势图

- 柱形展示每个时间桶的调用次数。
- 折线展示每个时间桶的可靠性成功率。
- 用途说明：判断失败率上升是否与流量突增相关。

### 7.4 Token 结构趋势图

- 堆叠面积图展示 Prompt、可见输出、Reasoning 和未分类差额；canonical 总 Token 作为独立总量展示，不把 raw Completion 与 Reasoning 重复堆叠。
- 用途说明：确认 Token 变化来自调用量、上下文或推理输出。

### 7.5 时间明细表

| 字段 | 说明 |
| --- | --- |
| 时间段 | `24h/48h` 显示小时，`7d/30d` 显示日期，均按 `Asia/Shanghai` |
| 调用次数 | 该时间桶调用数 |
| 成功 / 失败 / 超时 / 取消 | 结果数量 |
| 可靠性成功率 | 客户端取消不进入分母 |
| Prompt / 可见输出 / Reasoning / 未分类 / 总 Token | 与全页一致的 Token 结构和 canonical 总量 |
| P50 / P95 首响应 | 流式首响应分布 |
| P50 / P95 总延迟 | 完整耗时分布 |

用途说明：提供图表的精确数值替代，并支持按任意数值列排序。

## 8. 图表和视觉规范

- 使用 Apache ECharts，不手写 SVG 或 Canvas 图表。
- 延续 Zook Admin 的 Ant Design 组件体系，不引入第二套 UI 组件库。
- 页面采用克制、数据优先的运营后台风格；标题、字号、卡片和留白保持紧凑。
- 桌面宽屏采用两列或十二列栅格；窄屏自动改为单列。
- 图表不得覆盖标题、图例、筛选器或相邻卡片；坐标轴自动抽样，长名称使用省略号和 Tooltip。
- 表格首列可固定，过宽时仅表格内部横向滚动，不造成整页横向滚动。
- 排行图默认展示 Top 10，其余数据保留在完整表格；类别较多时使用 data zoom，不强行压缩轴标签。
- 交叉矩阵设置最小单元格宽度、固定行列标题和区域内双向滚动；整页不得出现横向滚动。
- 图表容器响应实际宽度变化并主动 resize，折叠/展开和侧栏变化后不得出现画布溢出或空白。
- 图表颜色使用色盲友好序列；成功/失败同时使用文字、图形和颜色表达。
- 图表必须配套用途说明、文字摘要、Tooltip、图例、空状态、加载状态、错误状态和可访问的明细表。
- 交叉矩阵单元格是可聚焦按钮，支持 Enter/Space 下钻，并提供包含 Provider、Model、指标和值的无障碍名称与清晰选中态。
- 动画保持轻量并尊重 `prefers-reduced-motion`。
- 所有数字使用本地化千分位；Token、百分比和毫秒单位保持一致。

## 9. 状态呈现

- **加载中：** 指标卡和图表使用固定高度 Skeleton，避免页面跳动。
- **无数据：** 明确说明当前筛选范围没有调用，不显示空坐标系。
- **加载失败：** 保留上次成功数据，在区域顶部显示错误和重试按钮。
- **部分数据缺失：** 例如 Provider 未返回 Token usage，显示“估算”或“缺失”标记，不以 `0` 冒充精确值。
- **自动刷新：** 刷新期间不清空现有内容，不打断用户当前筛选和滚动位置。
- **部分失败：** 页面使用同一 snapshot 时间；若只加载到部分区域，保留旧数据并持续显示“部分数据过期”，不把不同时间的数据伪装成同一快照。

## 10. 视觉与交互验收效果

- 使用包含长 Provider/Model 名称、10+ Model、多 route、缺失 usage、固定/自动策略和零数据的高密度固定样例验证页面。
- 在宽屏、`1280px`、`1100px`、`720px` 和窄屏检查：无元素重叠、无整页横向滚动、无标题/图例/筛选器遮挡、无过大字体或过量留白。
- 六张指标卡在宽屏为 3–6 列，在窄屏逐级降为 2 列和 1 列；控制栏可以自然换行且不挤压标签。
- 验证 Skeleton 高度稳定、长轴标签可读、表格内部滚动、图表 resize、键盘下钻、焦点可见和 reduced-motion。
- 验证筛选优先级、自动刷新保留状态、失效选项清理、`auto/fixed/全零回退/兼容回退` 的真实路由展示。
