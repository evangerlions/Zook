# Yaohezi M2 local protocol v1 (local implementation, not production acceptance)

Scope: trusted devices and self-subject authority, not family invitations, patient identity verification, clinical ingestion, sync or production enablement. Existing account login and self-asserted routing bindings are not health authority. M2 adds a separately authenticated trust root on an explicitly selected self subject. First bootstrap is allowed exactly once where no health authority has existed; revoked/lost devices never reset this condition.

## Cryptographic boundary

Each device owns immutable Ed25519 signing and X25519 wrapping public keys. Device ID is a random UUID, not a request header assertion. Bootstrap and each new session require a five-minute, one-use PostgreSQL challenge bound to account, subject, device descriptor and purpose plus the corresponding device signature. Existing trusted owner devices must approve enrollment, signing the complete candidate descriptor/challenge and explicit device permission. Account credentials alone cannot enroll into an existing authority. Enrollment in M2 is same-account only; restricted read devices use explicit resource UUID allowlists, not family access grants.

Management commands use domain-separated canonical JSON over a restricted JSON subset (integer numbers, ASCII field names, validated identifiers/base64url); exact objects reject unknown fields. Signatures cover every command field, subject, operation UUID and current authority epoch/version. Revision authorization envelopes bind version, subject/resource, operation, parent revision, actor account/device, device-grant version, key epoch, ciphertext digest, action and expiry. Verification authenticates routing only, never clinical truth. A verification response is not an ingestion credential; later M3 handlers must invoke the transactional guard again.

Resource keys are independent 256-bit DEKs. A TypeScript client reference uses RFC 9180 HPKE (DHKEM X25519/HKDF-SHA256, HKDF-SHA256, AES-256-GCM) to wrap exactly one resource/version key to one recipient device. Associated data binds subject, resource and resource-version UUID, recipient account/device/key, sender account/device, grant version and epoch. Ed25519 authenticates the capsule sender against a pinned trusted public key. The server verifies and stores opaque capsules, never executes HPKE decryption. No SQLCipher keys, profile-root keys or health plaintext belong in this API. A malicious authorized sender can put arbitrary bytes in ciphertext; the server cannot inspect those bytes. Client validation and resource-specific packaging enforce the application boundary.

An offline random 256-bit recovery secret independently derives an Ed25519 recovery signing seed and AES-256-GCM recovery-vault key with domain-separated HKDF labels. The encrypted vault contains only resource keys with resource IDs/epochs, never device private keys, login tokens, SQLCipher keys or current grants. The relay retains only the verifier public key and opaque encrypted vault. The secret remains offline; ordinary owner devices and caregivers do not automatically receive recovery custody. This reference is not the iOS portable-backup recovery code.

## Recovery and rotation

1. Trusted device available: new device proves its keys; an existing owner signs exact enrollment after out-of-band fingerprint confirmation. Only selected resource capabilities are issued. No automatic login-to-device enrollment.
2. Recovery secret only: reauthenticate the same owner account, fetch opaque vault, decrypt locally, prove recovery verifier and candidate private key against a fresh challenge/current recovery version. Atomically revoke all previous subject device grants and sessions, remove all relay capsules, increment key epoch and recovery version, replace recovery material, and trust only the new owner device. Historical resource keys can recover old content locally; future content needs fresh resource keys/new epoch. Old grants are never copied from the vault.
3. Neither: account login remains possible; bootstrap/session/recovery without an existing trust proof is denied. The relay has no decryption fallback or emergency bypass.

Device revocation and explicit rotation require a signed owner management command with fresh replacement recovery verifier/vault. Atomically revoke target/all relevant sessions, invalidate capsules, advance epoch/recovery version and replace offline recovery material. Old signed commands/recovery roots cannot be replayed. Remaining trusted devices must prove possession again to obtain new-epoch sessions and receive newly wrapped capabilities. Previously obtained keys/plaintext cannot be remotely erased.

## Persistence and authorization

Each protected call rechecks active product/account/membership, non-revoked device grant, role/resource scope, current grant version/epoch and unexpired hashed health-session token inside a per-subject PostgreSQL transaction. Session logout invalidates that token; device revocation invalidates every session of that device; recovery invalidates all old subject sessions. No positive authorization cache. A revocation serialized first rejects a later operation even if its account access token remains valid. An operation committed first is ordered before revocation, not retroactively erased.

PostgreSQL challenges are bounded per account, expire after five minutes and are consumed atomically. Health sessions live at most 15 minutes; bearer values are returned once, stored only as SHA-256 hashes and require matching signed operations. Device IDs and signing/wrapping keys are immutable. Management receipts are payload-hash-bound, checked only after current authorization; retries never resurrect revoked permissions. Audit rows contain minimal routing IDs/action/epoch, no keys, tokens, ciphertext contents or health values. All operations fail closed if durable storage is unavailable. Unknown device/subject details use generic rejection codes.

## Validation / launch boundary

Required local tests: first trust; second device approval; descriptor/key replacement; expired/used/cross-purpose challenges; wrong account/product; read-only signed medication mutation; cross-subject/resource replay; tampered capsule/signature/AAD; scoped recipient cannot decrypt another resource; recovery available/trusted-only/all-lost; old recovery root rejected after rotation; membership block; token expiry; immediate logout/device revoke; revoke-vs-operation order; server restart and concurrent bootstrap/recovery. Real PostgreSQL + Redis + loopback HTTP and normal account tokens are required. No schema-only acceptance.

Sources: [Ed25519 RFC 8032](https://www.rfc-editor.org/rfc/rfc8032), [HKDF RFC 5869](https://www.rfc-editor.org/rfc/rfc5869), [HPKE RFC 9180](https://www.rfc-editor.org/rfc/rfc9180), [hpke-js implementation](https://github.com/dajiaji/hpke-js), [Node crypto](https://nodejs.org/api/crypto.html). Independent review and final test evidence will be recorded separately. External cryptographic audit, native iOS trusted-device UI/storage integration and real-device interoperability remain release gates.

## Implemented framing and receiver trust

Recovery HKDF uses SHA-256, 32-byte output, and salt equal to signingBytes("recovery-context", {accountId,subjectId}). Signing seed info is "yaohezi-recovery-signing-v1"; vault KEK info is "yaohezi-recovery-vault-v1:" plus recovery version. Each vault uses a fresh random 12-byte nonce, AES-256-GCM with a 16-byte tag, and AAD signingBytes("recovery-vault", {version:1,accountId,subjectId,recoveryVersion}). Ciphertext is ciphertext||tag; all binary fields are canonical unpadded base64url. Vault plaintext has exactly version/keys; entries have exactly resourceId/resourceVersion/keyEpoch/key. Keys are 32 bytes. Duplicate tuples and credentials/private-key fields are rejected. JavaScript best-effort buffer clearing is not a secure-enclave or complete memory-erasure guarantee.

HPKE suite IDs are 0x0020/0x0001/0x0002, base mode, info signingBytes("resource-key-suite", {version:1}); AAD is signingBytes("resource-key-context", full context). Encrypted 32-byte DEKs produce 48-byte ciphertext. Each resource version and epoch gets an independent random DEK; historical keys are retained separately, never reused by rotateResourceKeys for future content.

All operations, including challenge issuance, acquire the same account advisory lock, then subject advisory lock, then authority FOR UPDATE and active app/user/membership FOR SHARE locks. Bootstrap has the advisory lock even before the authority row exists. Request-level legacy global transactions are bypassed for enabled M2 routes. This establishes commit order between revoke/recover and protected effects; active membership mutation is ordered against its share lock. No check-then-write outside this transaction is an ingestion capability.

Receiver loadTrustSnapshot uses configured HTTPS with no redirects/cookies/cache; only explicit test configuration permits 127.0.0.1 HTTP. It binds response nonce to the signed inspect operation and matches account/subject/epoch, with a 30-second validity bound. Independent root pins come from bootstrap fingerprint verification or recovery material verification, not the inspected relay key list. It validates active device grants and their required historical issuer chains. Each issuer must have proven owner authority, with exact signed candidate keys/account/subject/role/resources; a reader-signed owner certificate fails. Historical provenance and current epoch/revocation are separate: revoking an original issuer does not undo an existing legitimate child grant. Recovery-only devices validate from the new recovery root and do not need unrelated revoked bootstrap pins. Readers receive relevant active writer public authorization chains, not other readers' resources or keys.

Current snapshots rely on the configured authenticated relay for current routing/revocation freshness. Root/certificate signatures independently protect device-key and scope provenance. This is not a transparency log or malicious-relay rollback-proof protocol. M3 must add durable revision receipts/CAS, use the transaction guard at actual ingestion, and supply fresh trust state before accepting remote content; M4 must finish display-lease/offline enforcement. The reference verifier validates authorized envelopes only, not clinical truth or a persisted accepted revision.

Account-only access is independently gated from health devices. Both gates default off. Ordinary public logout retains its prior refresh-token contract; native clients that create health sessions must explicitly end those health sessions as part of sign-out. M2 health-session logout revokes that token; obtaining a fresh session again requires trusted-key possession and a new challenge. Device revocation invalidates trust and rejects even new session challenges. Native integration has not been shipped.

Root anchors use only a public descriptor, transcript digest and epoch/version metadata. bootstrapRootPin/recoveryRootPin verify the complete locally created signed transcript (including the recovery proof when applicable) before computing the public digest. Persist/transfer that anchor through the independently approved device/recovery channel only after the server transaction acknowledges success. Never initialize pins from inspect. The relay stores/returns this minimal root statement, not old vault ciphertext in historical certificates; the only recovery vault is the current encrypted authority vault. Native clients must journal replacement recovery material securely before submitting an irreversible rotation/recovery, and confirm offline custody; that user/storage flow remains a native release gate.
