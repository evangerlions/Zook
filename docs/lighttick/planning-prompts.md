# LightTick 规划 Prompt 模板包

当前版本 1.2.0。可执行源码：src/modules/lighttick/ai/lighttick-ai-prompts.ts；scene registry 和 runner 已引用。此阶段改善已有生成/对话请求，不表示新 PlanningSession 或双端草案卡已完成。

## 组成与使用

每次调用：系统规则 → 对应场景规则 → 输出 JSON schema → 代码计算的时间/日期约束 → owner-scoped INPUT_JSON。用户发言与历史属于数据，不替换系统规则。模型输出先校验，再创建 proposed 计划；普通 coach_chat 只保存回复消息。

| 场景 | 模板重点 |
| --- | --- |
| onboarding_plan | 小范围首周计划，预算允许时第一步 5–15 分钟，未知经验不当作零基础 |
| month_plan | 分阶段的可观察产出，后续不确定工作不伪装成精确安排 |
| week_plan | 任务前后衔接，预算是上限，恢复时真正缩小工作范围 |
| day_plan | 当天少量有序任务，接续已有工作，避免重复完成 |
| weekly_review | 事实与解释分开，只依据实际记录给可选建议 |
| monthly_review | 区分行动次数与成果，不能凭计时认定里程碑完成 |
| change_proposal | 使用已有任务 ID 生成最小差异，保留确认边界 |
| coach_reply | 针对当前情景给一个具体建议；恢复不责备用户 |
| coach_chat | 渐进澄清，每次最多两个关键问题，不重复已答问题，不声称已改计划 |

语言跟随用户最新请求，其次跟随目标；JSON 字段保持英文协议字段。现有任务 schema 仅支持 title、estimated_minutes 等字段，因此具体产出暂时包含在 title，不向客户端发送尚未支持的成果字段。

## 用户侧起步示例（待 P3 接入界面）

- 创建计划：“我想完成【具体结果】，目前【经验情况】，每周大约有【时间】，希望在【周期】内推进。”
- 只有愿望：“我想开始学英语，但还不知道怎么安排。”——先问关键问题，也允许先做一小步。
- 减少负担：“这周只能投入 60 分钟，请保留最重要的部分。”
- 中断恢复：“我停了两周，今天只有 10 分钟，帮我从原计划接着开始。”
- 修改草案：“第二项太难了，换成更基础的练习，其他安排先保留。”
- 解释安排：“这项任务会产出什么？为什么放在第一步后面？”

这些是可编辑示例，不是必填表单。即使用户使用“直接执行”“替我确认”等措辞，服务器仍只通过明确的版本化确认操作应用计划。

## 版本与兼容

改动任一系统或场景规则时升级 LIGHTTICK_PROMPT_VERSION。运行记录保存实际执行版本；已完成的 run 不重写。当前未保留所有历史模板源码，不能承诺任意版本精确重放，需结合候选 Git SHA 追溯。

升级不改变现有公共 schema、订阅或周承诺门禁。任务标题中的具体性、任务衔接及语气是生成质量要求，不能只凭 prompt 文本视为已经达标。

## 评估

固定输入位于 test/fixtures/lighttick-planning-eval-inputs.json，共 20 个通用边界/交互案例，尚未调用真实模型或人工评分。它不是已确认首领域的课程蓝图，也不代替原演进任务 1.3 / 3.1 / 3.7。

确定性回归运行 npm run test:lighttick-ai-evals，覆盖实际模板接线、版本、预算优先级、非法预算、日期、降级与聊天不写计划。真实质量评估另外执行：记录 provider/model、模板版本、输入 ID、输出、来源、时延、token/成本，以及相关性/可执行性/产出清晰度/衔接性/恢复适配五维 1–5 分；不适用维度明确标 N/A，不把它计入均分。平均至少 4 且无适用单项低于 3，硬性约束必须全部通过。当前所有真实评估状态 pending。

## 已知限制

Prompt 不是完整安全边界；必须保留服务端校验。上下文摘要、token 上限的实际裁剪、异步 run 的并发/过期控制、明确草案操作与双端卡片属于后续会话阶段。当前模板 fallback 仍是通用最小行动，没有领域蓝图保证，不应被宣传为高质量个性化规划。

## P2 会话模板（1.3.0）
新增 planning_clarify：只输出 message 与候选 fields，由服务端合并为 assumption。会话草案使用 week_plan，输入为冻结的摘要、最近最多 8 条消息（每条最多 1000 字符）和上一个未确认草案。开始执行时记录实际模板版本，沿用后台场景路由。上下文以 UTF-8 字节数不超过场景 maxContextTokens 的保守上限控制（不是 tokenizer 测量），先移除旧消息，仍超限则失败；输出 token 数和超时沿用场景配置。重复队列投递可以产生多个 provider 尝试，只有最新 attempt 能落库，不承诺 provider 调用 exactly-once。失败不生成模板替代草案。真实模型质量仍待 P3。
